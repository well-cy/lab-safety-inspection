## 二、BUG-007 修复指引（供前端参考）

已定位到具体代码位置，修复量很小：

1. **字段用错**（必须改）
   - 位置：`backend/static/index.html:363`
   - 现状：`$('v-count').textContent = \`共 ${r.total} 条记录\`;`
   - 改法：把 `r.total` 改为 `r.total_count`
   - 依据：接口 `GET /api/violations` 同时返回两个字段（`backend/main.py:195`），
     其中 `total` 保持契约原语义「本次返回条数」，`total_count` 才是符合筛选条件的总条数。
     **后端无需改动，契约字段定义见 docs/INTERFACE_CONTRACT.md §6.5。**

2. **缺少分页**（建议一并补上）
   - 位置：`backend/static/index.html` 的 `loadViolations()`（约 348-365 行）
   - 现状：调用 `/api/violations?` 时未传 `limit`/`offset`，页面也没有翻页控件
   - 改法：在函数内维护当前页，请求时带上 `limit`（每页条数）与 `offset`（跳过条数），
     并在表格下方渲染"上一页 / 第 N/M 页 / 下一页"
   - 依据：接口已支持 `limit`（默认 200，取值 1~1000）与 `offset`（≥0，默认 0），后端无需改动

3. **验证方法**：把 `/api/violations` 造出 200 条以上记录（或用 `limit` 观察
   `total` 与 `total_count` 的数值差异），确认统计文字与翻页均正确。

## 三、BUG-008 修复指引（供后端参考）

> **✅ 2026-10-15 已关闭**：马军 `0f557b6` 实现（魔数校验 + 首帧试解码，同步/异步双接口生效），
> 成员5 独立回归 45 项全部通过，详见 Bug 记录表"实际结果"列。以下指引保留作过程记录。

1. **现象与实测证据（2026-10-15）**
   - `POST /api/detect/video` 上传同一张 PNG → HTTP **200**，返回 `total_frames=1`，
     并生成 `annotated_vid_*.mp4`
   - `POST /api/detect/video/async` 上传同一张 PNG → HTTP **202**，任务最终 `status=done`
   - 对照：`POST /api/detect/image` 上传 `.txt` / 伪造 `.png` → 正确返回
     400「图片无法读取或格式不支持」
   - 结论：图片接口有类型校验，两个视频接口都没有

2. **建议改法（在入口显式校验，不依赖前端的判断）**
   - 位置：`backend/main.py` 的 `detect_video` / `detect_video_async`，
     或 `video/processor.py` 中 `process_video` 的开头
   - 做法：临时文件落盘后，用 `cv2.VideoCapture(path)` 打开并 `read()` 一帧；
     打不开或读不到帧 → 返回 `bad_request("不是有效的视频文件，请上传 MP4/AVI 等视频格式")`
   - 同步接口已有 `try/except ValueError → 400` 的框架，但当前图片会被"当作 1 帧视频"
     处理成功，异常并未抛出，所以必须在入口补一道显式校验
   - 异步接口需在**任务入队前**校验，否则用户拿到 202 之后只能从任务详情里看到失败

3. **验证方法**：分别用「PNG 改名为 .mp4」与「真实 MP4」调用两个视频接口 ——
   前者应返回 400（异步则任务 `failed`），后者应正常处理。

> 定级说明：本条定为**建议**级。原因是正常从界面操作时，前端会按 MIME/后缀
> 自动把图片路由到图片接口，用户踩不到；该问题主要在"改后缀文件 / 直接调 API"
> 场景暴露，属防御性、健壮性改进，故不作为功能缺陷夸大。
> 涉及 `backend/main.py`（成员3 独占）与 `video/processor.py`，未直接修改。
